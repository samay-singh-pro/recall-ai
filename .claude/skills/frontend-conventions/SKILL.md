# Frontend conventions

Goal: same as the backend. A new reader navigates in minutes, and adding, changing or deleting functionality touches one place. The `new-feature` and `commit-and-review` skills apply to frontend work exactly as they do to backend work.

## 1. Structure: one folder per feature

```
frontend/src/app/
  app.config.ts           providers: router, http client, interceptors
  app.routes.ts           top-level routes, each feature lazy-loaded
  core/                   app-wide singletons, no UI of its own
    auth/                 auth service, token storage, route guards
    http/                 interceptors (auth token, error handling), api base url
    config/               environment-driven settings
  layout/                 app shell: navbar, side menu, page frame
  shared/                 reusable UI pieces, pipes, directives, models used by 2+ features
  features/
    auth/                 login, sign up
    timeline/             tasks and reminders
    home/                 the main screen: add text, files, links; memories side panel with search
      home.routes.ts      routes for this feature
      memories-api.ts     the only place that calls this feature's backend endpoints
      memory.ts           type matching the backend schema (one file per type)
      home-page/          a routed screen: home-page.ts, .html, .scss, .spec.ts
      components/         small pieces used by this feature's screens
        memory-panel/     memory-panel.ts, .html, .scss, .spec.ts
```
File names follow **Angular's official style guide** (what `ng generate` produces in Angular 21): kebab-case, one concept per file, no `.component` / `.service` suffixes, each component in its own folder. Always create files with `ng generate` so names match the CLI.

A feature is a cohesive area of the product, not a single screen. New screens usually go into an existing feature.

### Dependency direction (never break)
`screen -> components`, and `screen/component -> <feature>-api -> core/http`
- Components never call `HttpClient` directly. Only `<feature>-api.ts` does.
- A feature never imports from another feature. Shared needs go to `shared/` or `core/`.
- `core/` and `shared/` never import from `features/`.
- `shared/` holds only things used by two or more features. Do not pre-emptively put things there.

## 2. Principles, applied with restraint
- **Single responsibility:** screen = one routed page's wiring; component = one visual piece; api service = HTTP; guard/interceptor = one cross-cutting concern.
- Standalone components only (no NgModules). Lazy-load every feature route.
- Smart/dumb split: screens fetch and hold state; child components take `input()`s and emit `output()`s and stay free of API calls.
- No abstraction for its own sake: do not create a store, facade or base class until real duplication or complexity appears.

## 3. Naming
- Any standard, conventional name is fine. The one requirement: **the name must say clearly what the thing represents or does.** Nothing random, vague or cryptic.
- Follow the Angular style guide as generated by the CLI: kebab-case file names that match the class (`memory-list.ts` holds `MemoryList`). Components, services and directives have **no type suffix**; guards, interceptors, pipes and resolvers keep a short one (`auth-guard.ts`, `auth-interceptor.ts`, `time-ago-pipe.ts`). Tests are `*.spec.ts`; routes are `*.routes.ts`.
- The backend-calling service is named for its job: `memories-api.ts` with class `MemoriesApi`.
- Classes PascalCase (`MemoryList`), variables and methods camelCase, constants UPPER_SNAKE_CASE, selectors prefixed `ra-` (`ra-memory-card`), already set as the project prefix.
- Methods: verb + object (`loadMemories`, `saveMemory`, `markTaskDone`). Booleans read as questions: `isLoading`, `hasError`.
- Use the user's vocabulary for domain things: `Memory`, `Task`, `Reminder`.
- Avoid cryptic abbreviations.

## 4. Routing and screens
- One route per screen, kebab-case paths: `/login`, `/signup`, `/home`, `/timeline`.
- Route params are named like the backend ids (`memoryId`) so the link between UI and API is obvious.
- Authenticated routes sit behind the auth guard; login and sign up redirect away when already logged in.
- Unknown paths go to a not-found page.

## 5. Talking to the backend
- Base URL comes from environment config, never hard-coded in an api file.
- One `<feature>-api.ts` per feature, with methods named after the action (`listMemories`, `getMemory`, `createMemory`). They return typed `Observable`s.
- Types (one file per type, e.g. `memory.ts`) mirror the backend schemas (`MemoryResponse`, `MemoryCreate`). When a backend schema changes, the matching model changes in the same PR.
- The auth interceptor attaches the access token and handles refresh. The error interceptor turns the backend's one error shape (`{"error": {"code", "message"}}`) into a user-readable message. Neither is duplicated in components.
- Never store tokens anywhere other than the one place in `core/auth`.

## 6. State and templates
- Use signals for component and page state. Use `OnPush` change detection.
- Every screen handles three states explicitly: loading, error, and empty. Not just the happy path.
- Templates stay simple: no business logic, no heavy expressions, no function calls that do work. Compute in the component (`computed()`) and bind the result.
- Use the new control flow (`@if`, `@for` with `track`).
- Forms are typed reactive forms with validation messages shown next to the field.

## 7. UI: PrimeNG
- Use PrimeNG components for UI (tables, forms, dialogs, toasts, menus). Do not hand-build what PrimeNG already provides.
- One theme configured once at app level. Colours and spacing come from theme tokens, not scattered hard-coded values.
- Wrap a PrimeNG component in our own `shared/` component only when it is configured the same way in three or more places.
- Screens must work on phone width as well as desktop.

## 8. Comments: short, uniform, useful
- Every class and every public method gets a **one-line JSDoc** saying what it is for: `/** Load the user's memories, newest first. */`
- Add a second line only for a surprising rule or side effect. No paragraphs, no restating the code, no commented-out code.
- Inline comments explain **why** something non-obvious is done, not what.
- Strict TypeScript: no `any`; every input, output and return type is explicit or clearly inferred.

## 9. Writing readable logic
- One function, one job. There is no hard line limit: a long function with a single job is fine.
- A long function with several steps is partitioned with blank lines and a short comment per step (`// 1. Validate`, `// 2. Send`, `// 3. Show result`). If steps are reusable or separately testable, split them out.
- Guard clauses and early returns; avoid nesting deeper than two levels.
- No magic numbers or strings: constants or config.
- Explicit over clever: no deeply chained RxJS operators when a few clear steps read better. Always unsubscribe through `takeUntilDestroyed` or the `async` pipe / `toSignal`.

## 10. Testing and tooling
- Add unit tests for every new component, service or guard, using the test runner the Angular CLI scaffolds. Follow `new-feature` for test quality: just enough coverage, assertions that would fail if the logic broke.
- Test behaviour a user would see (rendered text, emitted events, calls to the api with the right arguments), not internals.
- Mock the `<feature>-api.ts`, never call a real backend.
- ESLint and Prettier must pass with no ignored rules without a stated reason.

## Do not
- Call `HttpClient` from a component, or hand-write files the CLI can generate.
- Import across features, or add a new feature folder or dependency without asking.
- Put logic in templates.
- Hard-code URLs, tokens or colours.
- Leave a screen without loading, error and empty handling.
